# 相机查询失败恢复

主目录 `.`，`main`。

## 修复

原宿主在任意异常后设置 Failure，后续帧直接返回，使一次查询失败永久冻结镜头。

- 查询容量溢出、非法 sweep fraction 使用专门的 AlsCameraQueryException。宿主丢弃图与位置候选，下一次符合角色提交条件的帧重新采样当前场景；不累计失败时间、不重放过时查询。
- 成功后清除当前 Failure 和连续失败计数；保留累计次数和最近查询错误。每段连续失败仅首帧警告，避免每帧刷屏。
- 输入不合法、过期查询 owner、骨架绑定等错误仍终止相机并报错，不把所有异常都当作可重试。
- 换 owner 时先构造绑定和运行时、设置排除，再发布 owner 引用，避免构造失败留下半套绑定。

这是一项 Godot 宿主容错策略，不声称 UE 有相同异常处理协议。持续溢出期间镜头仍冻结，只有查询成功才恢复；没有隐藏错误或绕过碰撞。

## 验证方法

新增普通入口 `native_camera_recovery_smoke.tscn`。在实际肩部查询起点放置 70 个小碰撞盒，超过查询容量 64。角色胶囊明确排除这些盒子，相机仍查询实际 Jolt 场景，不注入模拟异常。

两轮均在创建障碍后切换肩部和鼠标控制视角，然后连续五帧断言：发生查询异常、累计计数递增、Frames/完整 FollowState/Camera3D 世界变换/FOV 与故障前完全相等。撤掉障碍后，下一帧必须成功提交且位置/旋转状态改变，当前错误清零，历史错误保留。第二轮恢复后继续运行三十个成功提交。

首轮使用覆盖角色的大碰撞盒未触发预期查询溢出，测试退出 1，保留 `artifacts/native-camera-recovery-first.log`；此夹具会同时干扰角色，改为实际肩部小盒和胶囊排除，没有放宽五帧失败/次帧恢复断言。

60 Hz 并行通过：两轮、10 次失败、52 次成功提交，日志 `artifacts/native-camera-recovery-isolated.log`。Optimize 构建 0 警告、0 错误。

30 Hz 单线程、120 Hz 并行同样各两轮、10 次失败、52 次成功提交，日志 `native-camera-recovery-30.log`、`native-camera-recovery-120.log`。每组只有两条预期查询警告，无错误，退出 0。

生产改动后重跑十四秒连续环境 60 Hz：墙/两平台各 149 采样、min ratio 0.45458964、换代通过，数值与前批一致。日志 `native-camera-environment-recovery-regression.log`，退出 0。
